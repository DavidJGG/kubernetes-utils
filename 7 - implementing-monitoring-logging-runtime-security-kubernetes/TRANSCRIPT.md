Monitoring and runtime logging are essential for securing Kubernetes clusters. You need to know what's happening in your environment before you can protect it. Kubernetes has comprehensive audit logging, but most Kubernetes distributions don't enable it by default, and the platform team hadn't configured it. Kubernetes audit logging is a powerful feature which you should enable in all production clusters. It captures every request to the API server, that includes authentication events, showing who connected and how they proved their identity. You configure logging with an audit policy. You specify rules to record access at different levels. None captures nothing, which is the default for most clusters. That's enough to know what happened, but not the details. A good option for secrets, RequestResponse captures both request and response bodies, giving complete visibility. That's what you want for sensitive updates like RBAC resources, at the cost of generating a lot of log content. Request captures the request body without the response. That's good for tracking access, where you don't want to see all the actual data, like lists of pods or services. The API server doesn't log audit events unless you explicitly configure a policy and tell it where to write the logs. With on‑prem clusters like K3S, you can set that as apiserver flags. Managed Kubernetes services have their own approach, integrating with other platform services, like CloudWatch for EKS and Log Analytics for AKS. Wired Brain's leadership has mandated full visibility into cluster activity that starts with an audit policy targeting the events that matter for security, RBAC changes, secrets access, exec operations into running containers. These are the actions attackers take during an intrusion. You also need to filter out the noise. System components constantly reading resources will flood your logs if you capture everything. And logs sitting on a node are useless if that node gets compromised, so you need to ship them to external storage where they're available for investigation. With proper audit logging, that 40‑minute attack would have generated dozens of traceable events.

### Understanding Runtime Visibility

With audit logging in place, Wired Brain Coffee ran a second red team exercise. This time every API call was captured, but the red team still compromised the cluster. They exploited a vulnerability in a web application to start a new process. They spawned a reverse shell inside a container. The attack took 20 minutes from initial shell to data extraction. None of this appeared in the audit logs. The API server only sees requests made to the Kubernetes API. If an attacker can execute a compromise inside a container, everything they do is under the radar. It all happens at the operating system level. Process execution, file access, network connections, these are system calls handled by Linux, invisible to Kubernetes audit logging. Containers share the operating system of the server they're running on. When a process inside a container makes a system call, that call goes directly to the host's Linux kernel. This is what makes containers so lightweight, but there are security implications. A compromised container can become a compromised server, and if you can monitor system calls on the server, you automatically get to audit everything happening in every container. EBPF, Extended Berkeley Packet Filter, runs in the Linux kernel on the server. It provides that system call observation. You can attach eBPF programs to kernel events, including system calls, and collect data about what's happening across the entire system. That includes all the calls made by containers because they run in the host kernel, too. That's Linux technology, but you can easily run it on all your nodes. And then you get system call visibility across your Kubernetes cluster. Falco provides that. It's a runtime security tool that uses eBPF to monitor system calls across all containers. Falco has three main components that run inside Kubernetes. The eBPF driver attaches probes to kernel events and streams out system call data. The rule engine evaluates each event against a set of detection rules. It's looking for patterns that indicate threats. When a rule matches, Falco generates an alert through configurable outputs, standard output, files, or external systems like Prometheus and Slack. Falco's default rule set detects common attack patterns out of the box, reading sensitive files like the shadow password file, connections to the Kubernetes API server from inside containers, searches for private keys or credential files, clearing logs to hide evidence. These rules encode decades of knowledge about how attackers operate once they gain access to a system. The red team's attack would have triggered multiple Falco alerts. Each event generates an alert with full context, the pod name, namespace, and the process and file involved. This context transforms a generic security event into actionable information that incident responders can immediately investigate.

### Container Immutability and Pod Security Admission

Wired Brain Coffee ran a third red team exercise with audit logging and Falco both active. Every step of the simulated attack was captured. The initial privilege escalation triggered a Prometheus alert within minutes. The reverse shell was detected as soon as it was spawned. API logs and Falco alerts all got forwarded to Elasticsearch. The security team had full visibility into what was happening, but the red team still accessed sensitive data. Between the first alert firing and the response team intervening, the attackers had enough time to read database credentials from secrets and exfiltrate customer records. Detection told Wired Brain they were under attack, but it did not stop the attack from succeeding. Prevention addresses this gap. Rather than alerting on dangerous activity after it begins, admission control blocks dangerous configurations before pods ever run. A container requesting root access, mounting the host file system, or configured with any other known insecurity gets rejected at deployment time. The attack surface shrinks because the capabilities attackers depend on aren't available. Container immutability is the core principle. An immutable container runs with the minimum capabilities needed and cannot be modified at runtime. That means no root access because processes running as root inside a container can exploit kernel vulnerabilities to escape. No privilege escalation because a process that starts unprivileged should never be able to grant itself elevated permissions. Read‑only file systems where possible, because attackers who gain code access need writeable paths to download tools and establish persistence. Kubernetes implements these controls through pod security standards, profiles which contain a set of security rules. There are three profiles. Privileged allows everything with no restrictions, which is usually only needed for system‑level workloads like logging agents that genuinely need host access. Baseline prohibits known privilege escalations. No host namespaces, no privilege containers, no dangerous capabilities. This blocks the most common attack vectors while remaining compatible with most applications. Restricted enforces the full set of hardening controls, non‑root users, dropped capabilities, read‑only root file systems, no privilege escalation. This is the target for production workloads, but not every app can function in a restricted pod. Pod security Admission, PSA, is the built‑in Kubernetes mechanism to enforce these standards. You apply labels to namespaces specifying which profile to enforce. The admission controller rejects any pod that violates the rules. This pod is defined with a root user, which is blocked by the restricted policy. PSA is an opinionated approach, and you can't modify the profiles or define your own, but it gives you a good security posture with no additional dependencies.

### Requiring and Applying Seccomp

In that demo, we enforced pod security standards across Wired Brain's namespaces. Baseline enforcement should be your minimum level. It blocks really dangerous configurations, privileged containers, and hostPath mounts. Normal application workloads don't need that level of access. Upgrading to restricted added further controls, blocking root access, and requiring containers to drop capabilities. The red team's container escape techniques won't work on a restricted namespace. We also hit the limits of PSA. You may not be able to make third‑party apps compliant. In that case, you'll need a vendor namespace with privileged enforcement. Pods can be deployed to that namespace with no protection at all. That's a gap that needs to be managed with namespace isolation and RBAC. There's another limitation. PSA validates pod configurations, but it can't fix them. We saw warnings when we deployed pods that they're configured without seccompProfiles. Seccomp is a Linux technology which filters sys calls at the kernel level. It blocks dangerous operations like mounting file systems or loading kernel modules. Kubernetes supports seccomp through the security context. You set seccompProfile type in the pod or container spec. Runtime default, uses the system defaults, which are fine for almost all applications. The restricted PSA profile requires this setting, but without PSA or at any other level, developers can omit it, and pods deploy without any system core filtering. Kyverno fills this gap with policy as code. Kyverno runs as an admission controller, intercepting API requests and evaluating them against your policies before resources are created. It can validate pod specs and reject those that don't meet the rules. That overlaps with PSA, but Kyverno also works as a mutating admission controller. You can inject defaults when developers omit them. So you could configure Kyverno to add Seccomp settings. Any pods deployed without Seccomp profiles would have them added by Kyverno, and then they would pass the PSA enforcement. A cluster‑wide mutation policy reduces the burden on development teams. It can fire against any pod resource changes, then set seccompProfile, type to RuntimeDefault, giving every container baseline syscall filtering. This is a safe security posture, which shouldn't impact legitimate applications at all. With PSA and Kyverno together, Wired Brain will have layered admission control. PSA provides the baseline security floor, no privileged containers, no root access, no dangerous capabilities with auditing and enforcement. Kyverno adds customization with a broader scope of rules and automatic injection of secure configuration to non‑compliant resources.
