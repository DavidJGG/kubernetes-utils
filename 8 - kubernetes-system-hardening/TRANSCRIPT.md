### Securing Static Manifests and Configuration Files

We'll start with one of the most fundamental aspects of Kubernetes security, the files on disk that define the control plane. Before we talk about APIs, permissions or network policies, we need to secure the configuration that actually tells Kubernetes how to run. If an attacker can change these files, they effectively control the cluster. No exploit is required, just access. And this is why control plane hardening always starts at the operating system and file system level. We'll focus on three categories of files. First, the static Pod manifests that define control plane components. Second, kubeconfig files that describe how clients authenticate. And third, certificates and private keys that establish trust within the cluster. Static Pod manifests are especially important because they define components like the API server, controller manager, and scheduler. The kubelet watches these files directly, so any changes here immediately affects how the control plane behaves without going through the API server. Kubeconfig files and certificates are often treated like simple configuration, but they represent identity and authority. If these files are exposed or modified, an attacker can gain legitimate access using valid credentials, which is much harder to detect than a traditional attack. In many environments, these files exist with default or inherited permissions. They may be readable by too many users, owned by the wrong account or stored in directories with overly permissive access. This usually isn't the result of negligence. It's simply the result of not having a clear, hardening baseline. A secure configuration is actually straightforward in principle. Critical files are owned by root, writeable only where absolutely necessary, and protected by strict directory permissions. This is least privilege applied at the file system level. The CIS or CIS Kubernetes benchmark provides a clear, concrete guidance here. It defines expected ownership and permissions for control plane manifests, kubeconfigs, and certificates. And throughout this course, we'll use CIS as a practical reference point, not as an abstract checklist.

### Securing etcd

Now we are going to focus on securing etcd. This is one of the most critical components in a Kubernetes cluster, because if etcd is compromised, the entire cluster is compromised with it. Everything else in Kubernetes depends on etcd being trustworthy. Etcd is the source of truth for the cluster. It stores the desired state of Kubernetes, configuration data, and depending on how your cluster is set up, sensitive information like secrets. If you want to understand the security posture of a cluster, you always need to start with etcd. From an attacker's perspective, etcd is an extremely high value target. Read access can expose secrets and internal configuration. Write access effectively means full control over the cluster, and this is why etcd needs stronger protection than almost any other component. Etcd is designed to be isolated. It typically runs only on control plane nodes, is not exposed publicly, and is accessed by a very small set of trusted clients. When etcd is reachable from places it shouldn't be, that's usually the first sign of a serious misconfiguration. Because etcd is accessed over the network, transport security is critical. Etcd is designed to use mutual TLS, or mTLS, for all client and peer communication. This means both sides of the connection authenticate each other before any data is exchanged. MTLS gives you three important guarantees. First, only authenticated clients can connect. Second, clients can verify they are talking to the correct etcd server. And third, all traffic is encrypted in transit. Without mTLS, etcd traffic is both vulnerable and unauditable. Even with strong transport security, etcd still relies on the underlying file system. Etcd stores all of its data in a directory on disk. And if an attacker can read or modify those files directly, encryption and authentication no longer help. And that's why directory ownership and permissions are so important. Etcd data directories should be owned by the dedicated etcd user with tightly restricted read and write access. Shared ownership or overly permissive permissions here effectively bypass higher level security controls. The CIS Kubernetes benchmark addresses both sides of etcd security. It defines requirements for enforcing mTLS and for securing the etcd data directory on disk, and this makes etcd security something you can clearly validate and audit.

### Hardening the API Server

Every single interaction with a Kubernetes cluster goes through the API server, whether it's a human using kubectl, a node reporting its status or a controller reconciling desired state. The API server is always involved. And that makes it the central control point of the entire platform and one of the most important components to secure. The API server is often described as the front door to the cluster, and that description is very accurate. All users, all nodes, and all internal components depend on it to function. If the API server is weak, it doesn't matter how well you secure everything else. A compromised or misconfigured API server effectively undermines the entire cluster. When a request hits the API server, it passes through several critical control points. First, authentication determines who the requester is. Then, authorization decides what they are allowed to do. And finally, admission control evaluates whether the request itself is acceptable. Together, these stages define the security boundary of Kubernetes, and they all live in the API server. One key thing to understand about the API server is that its behavior is almost entirely defined at startup. Security features aren't enabled dynamically. They are controlled by flags passed to the API server when it starts. That means hardening the API server is largely about choosing the right flags and making sure they are enforced consistently, which ties directly back to the static manifests we discussed earlier. Kubernetes is designed to work out of the box, but working by default does not mean hardened. Some defaults prioritize compatibility, ease of use or legacy support, not strict security. Left unchanged, these defaults can quietly introduce unnecessary risk without ever causing visible problems. And this is where the CIS Kubernetes benchmark becomes especially useful. CIS identifies which API server flags actually matter from a security perspective and explains why. It highlights unsafe options that should be disabled, protections that must be enabled, and configurations that auditors and security teams expect to see. Rather than guessing, CIS gives us a practical, structured checklist. The goal of the API server hardening is simple, reduce the number of ways into the cluster. That means limiting anonymous access, disabling legacy or insecure behaviors, and enforcing explicit permissions everywhere. Every access path you remove is one less opportunity for misuse, accidental or malicious. Hardening isn't only about prevention. It's also about visibility. If you can't see what's happening in your cluster, you can't protect it effectively. API server logging and auditing give you an insight into who is interacting with the cluster and how those interactions are changing its state. Audit logs provide a detailed chronological record of activity. They are essential for incident response because they show what happened and when. They support compliance by proving that controls are in place, and they enable forensics when something goes wrong. Every action leaves a trail if auditing is configured correctly.

### Restricting Network Access to the Control Plane

Up to this point, we've secured configuration files, hardened etcd, and protected the API server. Now we turn to network‑level security, limiting which systems can reach the control plane. Not every Pod, node or external system should have connectivity to those critical components. By controlling access at the network layer, we reduce risk before it even reaches authentication or authorization. Connectivity equals opportunity. If a component is reachable, it can potentially be attacked. Many incidents happen not because credentials were stolen, but because the wrong systems had network access to critical services. And this is why restricting network paths is one of the first steps in defense in depth for Kubernetes. Let's remind ourselves which components we are protecting here, the API server, which manages every request in the cluster, etcd, the source of truth for all cluster state, and controller manager and scheduler, which controls workloads and reconciliation. All of these are high value targets. Even a single exposed component can put the entire cluster at risk. By default, Kubernetes networks are often flat. That means internal communication is generally unrestricted. Flat networks are convenient, but they assume trust between nodes and Pods, and that assumption can be dangerous. A single compromised workload can pivot to the control plane if network restrictions are absent. To reduce risk, we apply network‑level controls as a layer of protection on top of authentication and authorization. And this includes firewall rules to block unnecessary inbound traffic to control plane nodes, network policies to restrict Pod‑to‑Pod traffic within the cluster, designing the cluster so only components that need access actually have it. Even if a vulnerability exists at another layer, a well‑designed network restriction slows or even stops an attacker. It's important to understand the difference between firewalls and network policies. Firewalls operate at the infrastructure level, controlling traffic to and from nodes. Network policies work at cluster level, restricting traffic between Pods. Both are complementary. Firewalls define the perimeter, and network policies limit lateral movement inside the cluster. The CIS Kubernetes benchmark emphasizes minimizing exposure to control plane components. Only required paths should exist, and everything else should be explicitly blocked. This is not about making the cluster inaccessible. It's about making access intentional, auditable, and secure. In practice, many clusters fail this test. Control plane nodes are reachable from every node in the cluster, no network policies exist to segment workloads, and firewall rules are overly broad or misconfigured. These are common and easy to fix, but they are also the kind of misconfigurations attackers and auditors notice first.

### Kernel Parameters and Node Security

In the previous module, we focused on hardening the Kubernetes control plane. In this module, we moved down to the worker nodes and the kubelet, where workloads actually run. Worker nodes are often treated as infrastructure details, but from a security perspective, they are a critical part of a cluster's trust boundary. A single misconfigured node can undermine otherwise strong control plane security. Kubernetes relies on the host operating system for isolation, scheduling, and networking. Kernel parameters, often configured using CIS control, control how the operating system enforces those boundaries. And many default values are intentionally permissive to support a wide range of workloads. But in a Kubernetes environment, permissive kernel settings can make container escapes, privilege escalation or denial‑of‑service attacks much easier. To reduce this risk, the CIS Kubernetes benchmarks define recommended kernel parameter values for worker nodes. These benchmarks focus on preventing common attack techniques and strengthening isolation between containers and the host. They're also widely referenced in audits, security assessments, and regulated environments. Aligning with CIS guidance gives you a clear, defensible baseline for node security. One of the biggest challenges with kernel parameters is configuration drift. Settings may change over time due to manual fixes, OS updates or automation applied inconsistently across nodes. Kubernetes itself does not continuously enforce kernel parameter values on worker nodes. And without explicit controls, insecure settings can quietly appear, even in otherwise well managed clusters. And this is where the kubelet becomes important from a security perspective. Because the kubelet runs with elevated privileges and interacts directly with the host, it's in a position to enforce security expectations. Rather than assuming the node is secure, the kubelet can actively check whether critical kernel parameters match secure defaults. The CIS benchmarks recommend enabling the protect‑kernel‑defaults flag on the kubelet. When this flag is enabled, the kubelet verifies that the key kernel parameters match secure values. If a node is misconfigured, the kubelet refuses to start rather than running an insecure state, and this fail‑fast behavior prevents weakened nodes from silently joining or remaining in the cluster.

### Limiting Kubelet Privileges

The kubelet doesn't just manage containers locally, it also authenticates to the Kubernetes API server. From the API's perspective, the kubelet is a highly trusted actor because it represents a node in the cluster. If that trust is too broad, a compromised node can escalate from node‑level access to cluster‑wide impact. In real‑world thread models, we assume that nodes can be compromised. That compromise might come from a vulnerable workload, a misconfigured container or direct host access. The critical question is not if a node can be compromised, but how far that compromise can spread. And without strong boundaries, node credentials can be abused to read or modify cluster resources. Kubernetes addresses this risk with the NodeRestriction admission controller. NodeRestriction enforces strict rules about what a node is allowed to do once it authenticates to the API server. Instead of trusting every request from a node, Kubernetes evaluates whether that request makes sense for that specific node identity. With NodeRestriction enabled, nodes can still perform the actions they need to function. They can update their own Node object, report status, and read information about Pods scheduled to them. What they cannot do is modify other nodes, access unrelated Pods or change cluster‑wide resources. But more importantly, node restriction blocks actions that could lead to privilege escalation. A node cannot modify another node's configuration, read unrelated secrets or tamper with cluster‑level objects. This significantly reduces the blast radius of a compromised worker node. The CIS Kubernetes benchmarks explicitly recommend enabling the NodeRestriction admission controller. This controller is designed to prevent node‑to‑cluster privilege escalation, one of the most dangerous failure modes in Kubernetes. Enabling NodeRestriction ensures that node credentials are scoped narrowly and used only for their intended purpose.

### Restricting External Kubelet Access

The kubelet exposes an API on each node, which is used to manage Pods, gather metrics, and perform administrative operations. While this API is essential for cluster operations, exposing it outside the cluster introduces a significant attack surface. An attacker who can reach the Kubelet API could potentially list, delete or manipulate Pods or escalate privileges to the host. Even with strong RBAC policies, a Kubelet API that is exposed externally can be misused. The API runs with the node‑level privileges, which are already highly trusted. And external access could allow an attacker to bypass Kubernetes security controls, access sensitive workloads or compromise the underlying node itself. To secure kubelet, the CIS benchmarks recommend restricting its API to trusted clients only. This can be done by binding the kubelet to localhost or an internal network interface or by using firewall rules to block external traffic. Additionally, enabling authentication ensures that even internal traffic is validated before it can perform privileged actions. CIS explicitly recommends that the Kubelet API should never be accessible from outside the cluster without authentication. This minimizes attack vectors and ensures that only authorized entities such as the control plane or approved administrators can interact with the node services. Enforcing network‑level restrictions add another layer of defense, making external attacks far less likely.

### Auditing ClusterRoles and RoleBindings

In this module, we focus on implementing least‑privilege RBAC in Kubernetes. RBAC, or role‑based access control, defines who can do what in a cluster. Overly permissive roles or misconfigured bindings increase the risk that a user or workload can escalate privileges, potentially compromising critical resources. Our goal is to ensure that every user, service account, and component has only the permissions they truly need. RBAC consists of two parts, roles or cluster roles, which define the actions that can be performed, and role bindings or cluster role bindings, which assign those permissions to specific users, groups or service accounts. Over time, roles can accumulate too many permissions or bindings can be applied too broadly. So auditing RBAC is critical because it helps us identifying situations where a compromised account could access more than intended. Some common signs of risky RBAC configurations include assigning cluster‑admin to multiple users or service accounts without justification, creating roles that use wildcard verbs or resources such as asterisks, which grant all actions, and granting service accounts privileges beyond what their workload requires. Each of these increases the potential blast radius if the account is compromised. The CIS Kubernetes benchmarks emphasize least privileged principles, audit roles and bindings regularly to ensure they are not overly permissive, avoid granting cluster‑admin or wildcard permissions unless strictly required, and ensure that service accounts are scoped narrowly to their workloads. Following these recommendations reduces the risk of privilege escalation and helps enforce strong separation of duties.

### Creating Constrained RoleBindings

After auditing RBAC, the next step is to enforce least privilege by creating constrained role bindings. Rather than granting cluster‑wide permissions, we scope roles to specific namespaces. This ensures that users and service accounts can only perform the actions they need in the areas where they operate, reducing the potential blast radius if an account is compromised. Namespace‑scoped roles allow us to restrict what users or service accounts can do within a single namespace. This prevents them from modifying resources outside their assigned namespace and keeps each workload isolated. Aligning roles with namespace boundaries makes privileged assignments predictable, auditable, and easier to manage over time. Role bindings connect roles to subjects such as users, groups or service accounts. When creating role bindings, it's important to assign only the permissions required for that account's workload. And following the principle of least privilege prevents users or workloads from gaining unnecessary access to resources that could be misused if compromised. CIS recommends limiting role bindings to the minimum necessary scope and avoiding unnecessary cluster‑wide privileges. Where possible, create dedicated service accounts for each workload and bind them only to the roles they need. This reduces the likelihood of privilege escalation and helps enforce strong isolation between workloads, users, and namespaces.

### Securing Service Account Tokens

Service accounts are used by Pods to authenticate with the Kubernetes API. Each service account is associated with a token that provides API access within the cluster. While convenient, these tokens are sensitive. If a token is over permissive or exposed, it can allow a compromised Pod to access resources beyond its intended scope. One key best practice is to limit where tokens are mounted. By default, every Pod receives a service account token, even if it doesn't need API access. Limiting token mounts to only those workloads that actually need them reduces the risk of accidental exposure or misuse and aligns with the principle of least privilege. Another important control is token lifetime. Long‑lived tokens increase the window of opportunity for attackers. By enforcing short‑lived tokens, we reduce the potential impact if a token is compromised, and Kubernetes can automatically rotate these tokens for long‑running workloads, ensuring continued access without compromising security. The CIS Kubernetes benchmarks explicitly recommend restricting service account token exposure. This includes disabling automount of the default token unless it's required, limiting token permissions to the minimum necessary API actions, and enforcing token rotation with bounded lifetimes. Following these recommendations reduces the risk of privilege escalation and protects sensitive cluster operations.
